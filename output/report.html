DosGuard - DoS Attack Detection & Prevention

Simulates three real denial-of-service attacks against a default-configured web server, shows legitimate users being locked out, then detects and stops each attack automatically.

1. The three attacks

AttackResource exhaustedWhy a default server fails
SYN floodhalf-open connection queueSpoofed SYNs never complete; each one holds a queue slot for 8 s.
HTTP floodCPU / request workersMore requests than the server can process; queue overflows, real requests time out.
Slowlorisconnection slotsSlow, never-finished requests hold every slot with almost no bandwidth.

2. How DosGuard detects and prevents

Detection ruleSignalAutomatic prevention
SYN_FLOOD>=100 SYN/s, <30% complete the handshake, backlog fillingSYN cookies (stateless handshake), block non-spoofed sources
HTTP_FLOODone IP >=50 req/s for 2 stemporary ban, doubling for repeat offenders
GLOBAL_OVERLOADtotal load >=90% of capacitymax-min fair-share rate limit; IPs with a clean history are exempt
SLOWLORIS>=10 connections from one IP still without request headers after 3 sblock IP + kill connections; hardening: 5 s header deadline, 20 connections/IP

Every ban expires automatically so mistakes heal themselves. Legitimate traffic includes a shared-IP office (15 req/s) and a power user (8 req/s), which a naive limiter would block.

5. Real-world mapping

The simulator applies each mitigation in memory. On a real Linux server they correspond to:

DosGuard actionReal command / setting
SYN cookies ONsysctl -w net.ipv4.tcp_syncookies=1
BLOCK <ip> for N siptables -I INPUT -s <ip> -j DROP (+ timed removal, or `ipset ... timeout N`)
max connections per IPiptables -A INPUT -p tcp --syn --dport 80 -m connlimit --connlimit-above 20 -j REJECT
per-IP request rate limitiptables -m hashlimit --hashlimit-above 50/sec --hashlimit-mode srcip -j DROP (or nginx limit_req)
header deadlinenginx client_header_timeout 5s; Apache mod_reqtimeout

python -m dosguard analyze-log access.log runs the same per-IP flood rule on a real nginx/Apache log and prints the iptables commands (dry-run).

6. Limitations (honest)

  • It is a simulation with simplified servers and attackers; the numbers describe the model, not a production system.
  • Thresholds (50 req/s per IP, 100 SYN/s, ...) are fixed and tuned for this model; a real deployment must tune them to its own baseline.
  • A very large shared-IP network (NAT) above the per-IP limit would be treated as a flood.
  • Sleeper bots that behave for a while build a good reputation and then escape the fair-share limit. A rate-only defence also cannot tell a busy office from polite bots; real systems add CAPTCHA / JavaScript challenges.
  • Volumetric floods that saturate the network link before reaching the server need upstream scrubbing / a CDN; software on the server cannot help.
